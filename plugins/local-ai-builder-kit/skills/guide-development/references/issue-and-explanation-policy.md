# Issue判断と教育的説明の規約

この文書を、開発依頼のIssue管理と、推奨・非推奨Actionを説明する方法の正本とする。
Issueは利用者へ操作を要求する課題表ではなく、Codexが裏側で保守する開発台帳として扱う。

## 1. 依頼を受けた直後のIssue判定

実装を始める前に、既存Issueを検索し、今回の依頼が次のいずれかに該当するか判定する。

Issueを必要とする:

- 独立してレビューまたは完了判定できるコード、文書、設定、配布物の変更
- 30分を超える、複数ターンにまたがる、または別タスクへ引き継ぐ作業
- 再現可能な不具合、セキュリティ上の懸念、データ境界の問題
- ADRを必要とする設計判断、不可逆な変更、外部公開
- 今は着手しないが、条件を満たしたら実施するバックログ
- Pull Requestを作る変更

Issueを必要としない:

- 質問への回答、用語説明、相談だけで成果物を変更しない
- 読み取り専用の調査、状況確認、要約、レビュー
- 既存Issueの完了条件内に明確に含まれる小さな作業
- その場で終わり、独立したレビュー対象を残さない可逆なローカル操作

境界では、Issueを増やすことではなく「6か月後に、なぜ変更したかを別の人が追えるか」で判断する。必要性が弱い場合は既存IssueのコメントまたはPR本文で記録し、新規Issueを作らない。

## 2. 重複確認

新規Issueの作成前に、対象リポジトリのopenとclosedを次の順で検索する。

1. 成果物名、機能名、エラー名など固有語
2. 利用者が得たい結果の言い換え
3. 同じ完了条件または同じ壊れるシナリオ

同じ結果を目指すopen Issueがあれば、新規作成せず本文・コメント・完了条件を更新する。closed Issueと同じ不具合が再発した場合は、再発証拠を付けてreopenできるか確認する。目的が似ていても完了条件や安全境界が異なる場合だけ、依存関係を明記して別Issueにする。

## 3. 外部投稿の承認

GitHub Issueの作成・更新・コメントは外部投稿である。利用者が現在の依頼でIssue操作を明示している場合は、その範囲で実行してよい。明示がない場合は、対象リポジトリ、タイトル、作成または更新する理由を示し、投稿直前に承認を得る。

下書き、重複検索、Issue本文案の作成までは承認前に進めてよい。利用者へGitHub画面の操作やIssue番号の入力を宿題として渡さない。

## 4. Issueの最低内容

Issueには次を含める。

- 解決したい問題または利用者が得たい結果
- 対象範囲と、今回はやらないこと
- 測定または確認できる完了条件
- 壊れるシナリオ、安全境界、必要な検証
- 依存Issue、根拠文書、着手条件または見直し条件

実装方法だけをタイトルにせず、結果が分かるタイトルにする。将来項目には着手条件を付け、現在の優先作業と区別する。

## 5. PRと完了時の更新

- PRがIssue全体を完了する場合は `Closes #<番号>` を使う。
- 一部だけを進める場合は `Related to #<番号>` とし、自動closeしない。
- 完了条件が変わった場合は、PR内だけで変更せずIssue本文も更新する。
- merge後にIssueの状態、検証結果、残る未決事項を確認する。
- 作業中に別問題を発見しても、現在の目的へ混ぜず、必要性を判定して別Issueへ分ける。

## 6. 推奨・非推奨Actionの説明

判断が必要な場面では、結論だけでなく、利用者が次回も判断できる短い説明を添える。順序は次とする。

1. 推奨または非推奨の結論
2. 利用者の目的へどう影響するか
3. 具体的な理由または壊れるシナリオ
4. 最も強い反論
5. 判断を見直す条件

非推奨Actionでは「規則だから」だけで止めない。何が失われるか、安全な代替Actionは何か、どの条件なら採用可能になるかを説明する。禁止境界を迂回する方法は提案せず、目的を満たす安全な代替へ導く。

説明は必要になった時点で2〜5文を目安に行う。利用者が理由を理解している場合や単純な読取操作では講義を挟まない。専門用語を使った直後に、利用者の目的との関係を平易な言葉で説明する。

## 7. 判定例

| 依頼 | Issue | 対応 |
|---|---|---|
| 「このエラーを直して」 | 必要 | 重複検索し、再現条件と完了条件を持つIssueへ関連付ける |
| 「このエラーの意味を教えて」 | 不要 | 説明だけ行い、変更が必要と分かった時点で再判定する |
| 「ログを見て原因を調べて」 | 原則不要 | 読取調査を行い、修正依頼へ移った時点でIssueを判定する |
| 「将来Web検索を追加したい」 | 必要 | 着手条件付きバックログとして記録する |
| 「mainへ直接pushして」 | 既存IssueまたはPRへ記録 | 履歴・検査を失うため非推奨と説明し、短命ブランチとPRを代替にする |
| 「表記を1文字だけ直して」 | 状況による | 独立PRならIssue、既存Issue内なら新規作成しない |

## 強い反論と見直し条件

この規約への最も強い反論は、Issue判定と理由説明が小さな依頼を遅くし、会話を儀式化することである。そのため、成果物を変えない依頼と既存Issue内の小作業では新規Issueを作らず、説明も判断が必要な場面に限定する。

Issueの半数以上が1週間以内に重複・不要として閉じられる、または理由説明が利用者の依頼より長くなる状態が5回続いた場合は、登録基準と説明量を見直す。ただし、外部投稿承認、重複確認、秘密情報保護は維持する。
