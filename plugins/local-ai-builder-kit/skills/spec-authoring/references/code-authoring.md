# コードを書くときの原則

code-rubric.md(レビュー観点)の双対。レビュアーに指摘される前に、書く側で潰す。

## 順序: 契約 → 壊れるテスト → 実装
1. **契約から書く**: 関数シグネチャ、APIスキーマ、DBスキーマを先に確定する。実装より契約のほうが変更コストが高い
2. **テストは「壊れるシナリオ」から書く**: 空入力、二重実行、途中失敗。ハッピーパスのテストは最後でよい(実装すれば大抵通るので情報量が少ない)
3. 実装は契約とテストを満たす最小で書く。「ついでの改善」はコミットを分ける

## 書く前の3つの自問(1行ずつでよい)
- **信頼境界**: この処理に届く外部由来データは何か。どこで検証するか
- **冪等性**: これが2回走ったら何が起きるか(リトライ、二重クリック、再デプロイ)
- **失敗の半径**: これが壊れたとき何が巻き添えになるか。ロールバックは1手か

## 防衛の層を決めてから書く
バリデーションは「UI / アプリ層 / DB制約」のどの層に置くかを意識的に選ぶ:
- **不変条件(絶対に破れてはいけない)** → DB制約に落とす(UNIQUE、CHECK、FK)。アプリ層のチェックは併設してよいが、DBが最後の砦
- **業務ルール(文脈依存で変わりうる)** → アプリ層。エラーメッセージをユーザー語彙で
- **入力形式** → 境界(Pydantic等)で一度だけ。奥で再検証しない
実例: 二重貸出防止を部分ユニークインデックスに落とした設計は、アプリ層チェックだけの設計より競合状態に強く、レビューで「変更不要」と評価された

## AIに実装させるときの指示の型
委譲プロンプトには必ず4点を含める:
1. 目的(1文)
2. 入出力の契約(型・スキーマ・例)
3. 完了条件(何が真になったら終わりか。「テストXが通る」形が最良)
4. 触ってはいけない範囲(ファイル、既存の公開インターフェース)
「いい感じに」で委譲しない。契約を書けないなら、まだ委譲できる段階ではない

## コメントとコミット
- コメントは why のみ(what はコードが語る)。「なぜこの順序か」「なぜこの値か」
- コミットは完了条件単位。動かない中間状態をコミットする場合は WIP と明記
