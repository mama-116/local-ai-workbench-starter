# 設計文書・計画レビュー ルーブリック

コードと違い、文書のレビューでは**書かれていないこと**が最大の指摘対象になる。

## 1. 問題設定は本物か
- 解こうとしている問題は、実在の証拠(データ、事例、頻度)で裏付けられているか
- 「解決策が先にあって問題を後付けした」兆候: 問題の記述が解決策の語彙で書かれている

## 2. 代替案
- 「何もしない」を含む代替案が最低2つ検討されているか
- 却下理由は検証可能か(「複雑だから」だけは理由として弱い)

## 3. 成功基準
- 完成の定義は測定可能か。「改善する」「使いやすくなる」は基準ではない
- いつ測るか、誰が判定するかが決まっているか

## 4. リスクとロールバック
- うまくいかなかった場合の撤退条件と手順があるか
- 一方向ドア(戻せない決定: データ移行、外部公開、契約)が明示されているか

## 5. スコープ
- 「ついでに」が混ざっていないか。フェーズ分けの境界は成果物単位で切れているか
- 明示的な「やらないことリスト」があるか

## 6. 責任と依存
- 各決定の決定者(1人)が名指しされているか。「チームで判断」は未決定と同じ
- 外部依存(他チーム、外部API、承認)とその遅延時の影響が書かれているか

## 7. 読者テスト
- この文書だけを渡された新任者が、質問ゼロで着手できるか。できない箇所が暗黙の前提

## ADHD特性を持つ作者向けの追加観点(このユーザー固有)
- 継続的メンテナンスを前提にした設計になっていないか。「1回きりの祭り」型と「放置しても壊れない」型に分解できるかを確認する
- 最初の一歩が30分以内に終わるサイズに切られているか
