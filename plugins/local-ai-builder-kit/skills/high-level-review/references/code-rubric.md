# コードレビュー ルーブリック

上から順に見る。上の項目でCriticalが出たら、下の項目は流し読みでよい。

## 1. 正しさ(目的との一致)
- diffは宣言された目的だけを達成しているか。無関係な変更が混ざっていないか
- 仕様の解釈が複数ありうる箇所で、どの解釈を採ったか明示されているか

## 2. 境界とエラーパス
- 空、ゼロ、null/None、最大長、負数、絵文字/マルチバイト
- 失敗時のリソース解放(ファイル、ロック、接続)。例外経路でもクリーンアップされるか
- エラーを握りつぶしていないか。ログだけ出して続行する箇所は妥当か

## 3. 状態と並行性
- 共有状態への同時アクセス。「今は1プロセスだから大丈夫」は前提として明記されているか
- 冪等性: 同じ処理が2回走ったら何が起きるか(リトライ、再実行、二重デプロイ)
- 時刻依存: タイムゾーン、DST、システムクロックの巻き戻り

## 4. 入力の信頼境界
- 外部由来のデータ(ユーザー入力、API応答、ファイル名、環境変数)がそのままSQL/シェル/パス/HTMLに到達する経路はないか
- 認可チェックは「誰が」ではなく「この操作をこのリソースに」の粒度で行われているか

## 5. 変更の影響範囲(blast radius)
- この変更が壊れたとき、何が巻き添えになるか。ロールバックは1手でできるか
- 公開インターフェース(API、DBスキーマ、ファイル形式)の変更は後方互換か

## 6. テスト可能性と保守
- テストは「壊れるシナリオ」を検証しているか。ハッピーパスだけのテストはテストがないのと近い
- 6ヶ月後の他人がこのコードの「なぜ」を理解できるか(コメントは what ではなく why)

## パフォーマンス(条件付き)
明らかなホットパス(ループ内I/O、N+1、大量データ)以外では指摘しない。推測の最適化提案は Nit 扱い。
