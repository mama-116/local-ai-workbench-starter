# ADR-0026: 開発PCではmerge済みmainの成功ビルドを起動する

- Status: Accepted
- Date: 2026-07-26
- Decision owner: 利用者

## Context

開発中のソースとWindowsポータブル版のEXEは別に存在し、Pull Requestをmergeしても既存EXEは自動で更新されない。そのため、利用者が古いEXEを起動して修正が反映されていないように見える。対象はこの開発PCだけであり、別PCへ配布したZIPの自動更新は求めない。

## Decision

固定したGitHubリポジトリの `origin/main` を最新版の正本とする。プロジェクト内の無視対象 `.local-runtime` に専用のdetached worktreeを作り、起動時に `origin/main` をfetchして追従する。commitごとにWindowsポータブル版を1回だけビルドし、ビルドと起動確認が完了した後に成功マーカーを記録して、そのEXEを起動する。

更新取得、worktree切替、ビルドのいずれかが失敗した場合は、成功マーカーとパス検査を通る直前のビルドだけを起動する。普段の作業worktree、未コミット変更、会話データは変更しない。二重起動されたランチャーは名前付きロックで1処理に限定する。

## Alternatives

- 何もしない: merge後も古いEXEを手動で見分ける必要があり、今回の問題が残るため却下。
- 普段の作業ブランチを起動時にpullする: 未コミット変更や実装途中のブランチを壊しうるため却下。
- ソースを毎回直接起動する: ビルド待ちはないが、配布版固有の依存・起動条件を確認できないため却下。
- GitHub Releaseから自動更新する: 配布PCにも拡張できるが、署名、配布物検証、更新UIが必要で、開発PC限定の目的には過剰なため却下。

## Consequences

- merge済み変更は、次のランチャー起動時に取得・ビルドされる。
- 同じmain commitの2回目以降は再ビルドしない。
- 新しいcommitの初回起動はWindowsビルド完了まで待つ。
- ネットワークまたは新規ビルドが失敗しても、直前の成功版を利用できる。
- commit単位のビルドを自動削除しないため、利用を重ねるとディスク使用量が増える。

## Review condition

成功ビルドが5件または合計2GiBを超えた場合は、実行中EXEを削除しない世代管理を追加する。別PCでも自動更新が必要になった場合は、署名済みReleaseとハッシュ検証を別ADRで設計する。起動待ちが日常利用を妨げる場合は、merge後のバックグラウンド事前ビルドへ見直す。
