# ADR-0008: 観測機能をアプリ内の交換可能な取得部品として構成する

- Status: Accepted
- Date: 2026-07-16
- Decision owner: 利用者

## Context

複数のOllama接続先とモデルを比較するには、体感だけでなく応答時間、トークン数、CPU、RAM、GPU、VRAMを実行単位で確認できる必要がある。観測機能全体を動的プラグインにすると、読込み、互換性、署名、安全確認の仕組みが先に必要になる。一方、特定GPU向けの処理を会話Serviceへ直接書くと、Windows PC、DGX Spark、将来のAMD GPUで作り直しになる。

## Decision

- 観測機能はCodexプラグインや外部監視アプリへ依存させず、完成アプリ内のApplication Serviceとして持つ。
- OSやGPUから値を取得する部分だけを `TelemetryCollector` 相当の契約で交換可能にする。
- 初期の取得部品は、Ollama実行情報、このWindows PCのCPU・RAM、`nvidia-smi`によるGPU・VRAMに分ける。
- Ollamaから得られる総処理時間、入力・出力トークン数は、接続先にかかわらずrunへ関連付ける。
- CPU・RAM・GPU・VRAMは取得元端末を明記し、取得できない項目は0で埋めず「未取得」として保存する。
- DGX Sparkの詳細なハードウェア情報は、Ollama APIへ責務を混ぜず、将来のLAN観測部品で追加する。
- 観測データは `LOCAL_OPERATIONAL` としてSQLiteだけへ保存し、外部送信しない。
- 観測の失敗、タイムアウト、対応外GPUは会話生成を失敗させない。失敗理由だけを安全な実行ログへ残す。
- 動的プラグインの探索・読込み・インストール機構は現段階で作らない。

## Alternatives

- 観測機能全体を動的プラグインにする: 後付けには強いが、現在必要のない互換性・安全管理が増えるため不採用。
- 会話ServiceへWindows/NVIDIA処理を直接書く: 最短だが、別端末や別GPUへ交換できないため不採用。
- 外部監視アプリだけを使う: 高機能だが、会話runとの正確な関連付けが難しいため補助用途に限定する。
- Codexプラグインにする: 開発中は便利だが、完成アプリがCodexなしで観測できなくなるため不採用。

## Consequences

- 会話、保存、観測を分離したまま、実行単位の性能比較ができる。
- 対応ハードウェアを増やす際は取得部品を追加すればよい。
- 最初はローカルPCの詳細値と、LAN側Ollamaの実行値で観測範囲に差が出る。
- 高頻度サンプリングはDB容量と負荷を増やすため、開始時・生成中の間引き・終了時の最小記録から始める必要がある。

## Review condition

第三者が観測部品を配布する必要が生じた場合に限り、動的プラグイン化、署名、互換性、権限、無効化方法を別ADRで検討する。DGX Spark側へ常駐処理を置く場合も、導入とLAN公開範囲を別途確認する。
