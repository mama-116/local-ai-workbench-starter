# ADR-0015: 承認付きメモ帳課題からコンピュータ操作を始める

- Status: Accepted
- Date: 2026-07-17
- Decision owner: 利用者

## Context

利用者は、デスクトップ画面を認識し、マウスとキーボードで一連の操作を行い、将来はゲーム内の選択も任せたい。現状は読み取り専用Tools/MCPまでで、画面操作の承認、対象再検査、停止、監査契約がない。

純粋な画像座標操作は独自描画画面へ広げやすい一方、画面位置の変化で誤クリックしやすい。UI Automationだけではゲーム等を扱えない。最初から両方の実行経路を実装すると、失敗原因と安全境界を切り分けにくい。

## Decision

- 初回課題を「メモ帳を開き、指定文を入力し、保存しない」に固定する。
- スクリーンショットで画面全体を観測し、UI Automationで対象アプリと編集領域を検証する。画像座標だけのクリックは初回実装しない。
- アプリ起動は固定された `windows_notepad` プロファイルだけを受け付け、モデルへ実行ファイル、パス、引数を渡させない。
- 起動、固定ターゲット、文字入力の計画全体を表示し、利用者の1回承認後だけ実行する。メモ帳起動後に、固定ターゲットプロファイルから現在のUIA要素を解決し、0件または複数候補なら停止する。
- 最大5操作、60秒、同時1件、承認待ち30秒とする。各操作の直前と直後に状態を再取得し、予想外なら停止する。
- アプリ内停止と `Ctrl+Alt+F12` を用意し、停止要求後は押下中のキーとボタンを解放して自動再開しない。
- 物理キー入力は1 Unicode scalarごとに前面とフォーカスを再検査し、初回は秘密情報を含まない試験文だけを許可する。競合後に別アプリへ2文字以上到達した場合は物理キーProviderを撤退する。
- スクリーンショットとUI構造をPRIVATEとしてローカル保存してよい。初回は自動削除せず、合計250MiBで新規実行を止める。
- 5回連続を試作合格、異なる画面条件を含む10回連続を初版合格の仮基準にする。
- ゲーム向け画像座標操作、オンラインゲーム、購入、アカウント変更は別ADRまで実装しない。

状態値、承認区分、保存単位は [ARCHITECTURE.md](../ARCHITECTURE.md)、詳細な契約と受入基準は [COMPUTER_USE_DESIGN.md](../COMPUTER_USE_DESIGN.md) を正本とする。

## Alternatives

- 何もしない: 誤操作は増えないが、利用者が望む操作の必要性と実現性を検証できないため不採用。
- 画像と座標だけで始める: ゲームへ近いが、初回から誤対象を意味で再検査できないため不採用。
- UI Automationだけで完結する: 初回は安全だが将来の独自描画UIへ拡張できないため、観測はハイブリッド、実行はUIA検証済み対象に限定する。
- UI-TARS Desktop等を直接統合する: デモは早いが、本アプリ側の固定許可、監査、無料運営ガードを保証できないため不採用。

採用案への最も強い反論は、観測と実行で複数の技術を扱うため保守範囲が増えることである。初回は単一アプリ、単一モニター、3操作へ絞り、純粋な画像クリックを延期する。

## Consequences

- 永続的変更を残さず、画面認識、承認、マウス、キーボード、停止、監査を一周検証できる。
- UI Automationが提供されないゲーム画面は初回に操作できない。
- 画面画像とUI構造がPRIVATEデータとして蓄積するため、容量と配布物混入を検査する必要がある。
- Plannerが誤っても、固定スキーマ、アプリ許可、計画承認、直前再検査が別々に拒否できる。

## Acceptance criteria

- [COMPUTER_USE_DESIGN.md](../COMPUTER_USE_DESIGN.md) の `CU-AC-01` から `CU-AC-09` を満たす。
- 承認なし、前面変更、未知アプリ、制御文字、上限超過、停止、Ollama停止、強制終了を自動試験または実機試験で確認する。
- 本物のOS入力へ進む前にFake Providerの壊れるシナリオ試験を通す。

## Review condition

メモ帳課題が異なる画面条件で10回連続成功した後、自動化候補を検討する。UI Automationで対象を取得できない需要が具体化した場合だけ、隔離環境と規約確認を含む画像座標操作の別ADRを作る。30日間に本人利用が0回ならゲーム対応へ進まない。
