# ADR-0014: 読み取り専用Tools/MCPを右側管理欄から始める

- Status: Accepted
- Date: 2026-07-17
- Decision owner: 利用者

## Context

ローカル資料を会話中に探して読めるようにしたい。一方、モデルが自由にファイル、シェル、ネットワークを操作できる構成は、許可外データの読取りや意図しない変更につながる。MCPサーバーはアプリとは別に動くプログラムであり、サーバーが申告する「読み取り専用」という情報だけでは安全性を保証できない。

初回画面では日常の会話領域を保ちつつ、何を許可し、何を読んだかを利用者が追える必要がある。履歴が少ない段階から専用管理画面を置くと、機能に対して画面が過剰になる。

## Decision

### 機能範囲

- 会話ごとに利用者が選んだ1フォルダーだけへ、一度の読取許可を与える。許可は取り消せる。
- 内蔵ツールは、フォルダー内検索とテキスト読取りの2種類から始める。
- 初回対象はUTF-8の `.txt` / `.md` とし、1ファイル1MiB、検索20件、1回の利用者発言につきツール呼出し3回、結果合計64KiBを上限とする。
- ツール呼出しは順番に実行し、1回10秒で打ち切る。検索と読取りの後にOllamaへ結果を返し、最終回答を生成する。
- Ollamaがツール呼出しに対応しない場合はツールを無効化し、通常会話を継続する。

### 安全境界

- 選択フォルダーは解決済み絶対パスとして保存する。ツール引数には許可IDと相対パスだけを渡す。
- `..`、絶対パス、許可フォルダー外、シンボリックリンク、ジャンクション、再解析ポイント、非対応形式、上限超過を拒否する。
- `.env`、秘密鍵、認証情報、SQLite、Git管理領域、Ollama設定、アプリの個人データ領域は許可フォルダー内でも拒否する。
- 書込み、削除、シェル、外部ネットワーク、MCP Resources、Prompts、Sampling、Tasksは初回対象外とする。
- ローカルMCPは `stdio` 接続1件だけとする。コマンド、引数、実行ファイルのSHA-256、許可ツール名を固定した、利用者が信頼済みとして登録したプロファイルだけを使う。
- `cmd.exe`、PowerShell、WSL等のシェルを経由するプロファイルと、秘密情報を環境変数へ渡すプロファイルを拒否する。MCPの自己申告だけで読取専用とは判定しない。
- 外部MCPプロセス自体が何を読むかはアプリから完全には制御できない。初回の自動実行対象は同梱または内容を確認済みの読取専用サーバーに限定し、任意の第三者MCP登録は別の安全設計まで延期する。

### 実行と記録

- Application層に `ToolCoordinator` を置き、Ollamaのツール要求、許可検査、Provider実行、結果返却、監査保存をまとめる。UIからProviderを直接呼ばない。
- 内蔵読取とMCPは同じ `ToolProvider` 契約を実装する。MCP依存はInfrastructure層だけへ閉じ込める。
- 各呼出しへUUIDを付け、会話、run、Provider、ツール名、入力、状態、開始・終了時刻、失敗理由、結果本文、結果サイズ、SHA-256をSQLiteへ保存する。
- 状態は `pending`、`running`、`completed`、`failed`、`denied` とする。再実行は元記録を上書きせず、新しい呼出しとして追加する。
- 結果本文は正確な会話経路の再現に必要な上限付きPRIVATEデータとして保存する。通常ログには本文を重複出力せず、画面の一覧では短いプレビューだけを表示する。
- 失敗や拒否でアプリを停止しない。AIへ利用可能な結果だけを返し、利用者には短い理由と監査記録への導線を表示する。

### 画面

- 初回はA案を採用し、右側 `CONTROL DESK` に許可フォルダー、利用可能ツール、実行中表示、直近結果、監査記録を開く操作を置く。
- 回答吹き出しには「資料を何件読んだか」だけを表示し、詳細は監査記録で確認する。
- 監査履歴が100件以上になるか、利用者が右側だけでは追いにくいと判断した後、A案を維持したままC案の専用 `Tool Center` を追加する。

## Alternatives

- B案の実行トレイ: 回答とツール呼出しの関係は追いやすいが、日常会話の縦幅を圧迫するため不採用。
- C案を最初から設置: 大量履歴の管理には強いが、初回の2種類の読取ツールとMCP 1件には過剰なため後続とする。
- 任意のローカルMCPを警告だけで登録: 拡張は速いが、別プロセスの読取り・通信・変更をアプリが保証できないため不採用。
- MCPの `readOnlyHint` だけを信頼: 実装は簡単だが自己申告であり、安全境界として弱いため不採用。

## Consequences

- 選択フォルダー内の資料を、会話画面を離れずに安全側の上限付きで利用できる。
- 全呼出しを後から確認でき、許可取消し後の読取りを拒否できる。
- 初回MCPは自由なプラグイン市場ではなく、確認済みプロファイル1件に限定される。
- 検索後にファイルを読むため、通常会話よりOllama往復と待ち時間が増える。
- MCP SDKを導入する場合は安定版1系を上限付きで固定し、2系安定版へ移る前に互換試験が必要になる。

## Acceptance criteria

- 許可フォルダー内の対応ファイルだけを検索・読取りできる。
- 許可外、パストラバーサル、リンク経由、秘密情報候補、非対応形式、上限超過をテストで拒否できる。
- 許可取消し、未知ツール、壊れた引数、MCP停止、タイムアウトでも会話アプリが継続する。
- 1発言の上限を超える呼出しを実行せず、各結果と拒否理由が監査記録へ残る。
- ツール非対応モデルでは読取機能を無効表示し、通常チャットは従来どおり動く。
- 実行中表示があり、Fletの入力と停止操作をブロックしない。
- PRIVATEデータを公開ネットワークへ送らず、`strict_free` を通過したローカルProviderだけを使う。

## Review condition

監査履歴が100件以上になるか、右側管理欄で目的の呼出しを探しにくくなった時点でC案を追加する。第三者MCPが必要になった場合は、OS分離、ネットワーク遮断、署名またはハッシュ更新、配布ライセンスを別ADRで決めるまで自動実行を広げない。

MCP Python SDK 2系が安定版になった後、1系固定の互換性と保守費を見直す。
