# 過去資産の再利用方針

## 採用するパターン

### fable-perspective

- 発散と収束を混ぜない
- 決定、仮置き、未決を分ける
- 問題、成功基準、やらないこと、代替案から設計する
- 契約、壊れるテスト、実装の順に進める
- 作成者とレビュアーの役割を分ける

`discussion`、`spec-authoring`、`high-level-review`をPluginへ移植した。初心者はSkill名を覚えず、`guide-development`から必要な工程へ案内される。

### ai-dev-kit

- GitHub Flow
- 作業開始時の対象確認
- 完了条件単位のコミット
- テスト、レビュー、PRを出荷ゲートにする
- 外部への変更や破棄系操作は人間の承認を得る

ただし、初心者へ10個のSkill名を覚えさせない。`guide-development` が必要な作業を選び、利用者へは目的だけを伝える。

### KAIROS OS

- UIモックを先に作り、選択後にバックエンドへ進む
- Next.js系フロントエンドとFastAPI系バックエンドを分離する考え方
- Ollama、RAG、AIチャットをフェーズ分けする
- 要件、基本設計、API、テスト、Git運用、マニュアルを残す

KAIROS OSのコードやPrivate文書は、そのまま配布ZIPへコピーしない。

## 採用しないもの

- Issue番号を利用者に入力させる操作
- すべてのタスクでブランチ名やGitコマンドを説明すること
- 未検証の長時間自律実行
- 過去プロジェクト固有のバージョン、ラベル、リポジトリ名

## 変換原則

過去資産を「読む教材」から次へ変換する。

- 判断手順はSkill
- 強制したい規則はHookまたは検査スクリプト
- 記録形式はテンプレート
- 技術固有情報は参照文書
- 個人情報と生ログは移植しない
